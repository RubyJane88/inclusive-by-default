The usual tests pass on a page that a keyboard or screen reader user cannot use. Tests that find controls by role and name fail on it, and say how to fix it.

What a screen reader gets

The browser turns the page into a tree of roles and names. Screen readers read it, and so do AI agents that use Playwright MCP. Unnamed controls on the broken page have no name here either.

What scanners cannot see

The broken dialog has correct ARIA: a dialog role, marked modal, with a name. A scanner reads markup and cannot press keys, so it has nothing to say about what happens when you do.

The focus contract, in five steps

StepThe test checksIf it fails, the Fix line says
1The dialog opensuse <dialog> with a heading that names it
2Focus moves into the dialoguse <dialog> and open it with showModal()
3Tab and Shift+Tab stay insideshowModal() makes the page behind inert
4Escape closes the dialoguse <dialog>: Escape closes it natively
5Focus returns to the button that opened ituse <dialog>: closing it restores focus

Focus may step out to the browser’s own controls, as Chromium does once per cycle. It must never reach the page behind the dialog. The test checks the keyboard path written in it, not every path.

Two checks, two answers

axe checks that a name exists. The name check asks whether it says anything.

What the name check rejects

RuleExample that fails
No name at all(empty)
A generic word“icon”, “image”, “click here”
A name that repeats the role“Submit button”
A file name or id“img_001.png”
Visible text missing from the name“Save” on a button that shows “Save draft”

It rejects known-bad names. It cannot tell whether a plausible name is right: “Settings” on a delete button passes. People still review names.

The tests

Take it home

You do not need a new tool. You need the tools you already have to run on every test, and to say what to fix. Copy these in order. The examples use Python, pytest and Playwright; the ideas work in any stack.

1 Start in 15 minutes: axe after every test

One file. axe runs after every test that uses Playwright’s page, and the test fails if axe finds WCAG A or AA problems.

  1. Install, if you have not already: pip install pytest-playwright, then playwright install chromium.
  2. Copy the file below into your tests folder as conftest.py, or download conftest.py.
  3. Put axe.min.js next to it (axe-core {{meta:axe}}, MPL-2.0).
  4. Run your tests.

To skip the check for one test, you must say why. A blank reason stops the whole run.

If it fails on day one with many violations, that is normal. Start with one test file, fix or ticket what it finds, then widen it.

2 Find elements by role and name

Tests that find elements the way assistive technology does fail when a control has no name. You get that check for free.

To make it the default, wrap the page in an object that only offers role-based methods: a11y_page.py. The missing methods are the point.

3 Make failures say the fix

More examples: messages.py.

4 Ban names that say nothing

Add your own words: internal codenames, “TODO”, placeholder text. The full rules are in name_problem in helpers.py.

5 Add one behavior check for your riskiest component

Write down what a keyboard user must be able to do, then test exactly that. For a dialog: it opens, focus moves in, focus stays in, Escape closes it, and focus returns. The working version is assert_modal_focus_contract in helpers.py. Use the same idea for a date picker, a menu or tabs.

6 Use it with AI assistants

AI assistants fix accessibility problems well once they are pointed out, and rarely raise them on their own. Your tests do the pointing. These are suggested starting points; they were not tested in the talk.

A rules file asks. A test enforces. Use both.

What automation will not catch

These checks are a floor, not a ceiling. Passing them is not WCAG conformance. Once per release, for each key flow, take ten minutes:

  • Keyboard only. Can you reach and use everything? Can you always see where focus is?
  • Screen reader. Tab through the flow. Does every control announce what it does?
  • Zoom to 200%. Does anything overlap, get cut off, or need sideways scrolling?

Nothing replaces testing with disabled people.
